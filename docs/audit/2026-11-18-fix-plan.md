# Fix plan for the 2026-11-18 audit

Work in this order. One commit per step (or per coherent sub-step), each
building and passing tests. Finding numbers refer to `2026-11-18-audit.md`.

Run every cargo command through `build-slot` from `frameworks/moose`
(`build-slot cargo test -p moose-clap`, etc.). Before the PR, run
`build-slot tools/verify.sh` from the repo root: it also checks the plugins
under `plugins/` that use moose, and any API change must land with their
fixes in the same PR.

## Step 1: serialize state on demand, on the host thread (findings 1, 2)

Goal: a save always reflects the last load and the live custom state, and
nothing serializes on the audio thread unless the plugin opts in.

- The host-thread save path reads custom state directly when it can own the
  plugin (inactive, or active but not processing), and otherwise asks the
  audio thread for a fresh snapshot at the next block boundary, with a bounded
  wait, before falling back to the last published snapshot. Pick the simplest
  design that meets this; document the choice in the code.
- A load while active but not processing (`processing == false` in CLAP,
  VST3 between `setProcessing(false)` and `(true)`) applies synchronously on
  the host thread, same as the inactive path.
- The per-block publish runs only for plugins that implement `snapshot_into`
  or `snapshot_version`; the default no longer calls `save_state` on the
  audio thread.
- The editor's `state_changed` fires after the state is applied.
- Tests: CLAP and VST3 load-then-save while active-not-processing returns the
  loaded custom state; a `save_state`-only plugin performs no audio-thread
  allocation (use the `rt-paranoid` checker).

## Step 2: report load failures, free off the audio thread (finding 4)

- When the load is applied synchronously, return the `load_state` error to the
  host (`false` / `kResultFalse` / AU error).
- When it must be deferred to the audio thread, validate on the host thread
  first (envelope parse plus an optional `validate` hook), so the deferred
  apply cannot fail on framing.
- Apply `#[persist]`, params and extra as one unit from the host's point of
  view (no torn window visible to a save).
- Hand the consumed `DeserializedState` back to a non-audio thread for
  dropping (a return slot drained on the main thread is enough).

## Step 3: fix the `reset` contract (finding 3)

- `prepare` (activate, may allocate, main thread) and `reset` (clear state,
  may run on the audio thread, must not allocate) become distinct in the docs
  and in the default impls. Keep source compatibility where possible: the
  default `prepare` keeps calling `reset`.
- Wrap wrapper-driven `reset` calls in the `rt-paranoid` section.
- Update `docs`, the trait docs and examples that allocate in `reset`.

## Step 4: latch after a panic (finding 5)

- After the first caught panic in `process`, mark the instance failed: output
  silence, skip the plugin, report the error status once, log once. Clear the
  latch on the next successful `activate` / `prepare`.
- Logging from the audio thread: record the message in a preallocated slot
  and print it from the main thread.

## Step 5: smoothing correctness (findings 6, 7)

- `FloatParamReadF64` reads at `f64` end to end (no `f32` round trip).
- `next()`, `next_after()` and `next_into()` share one snapping rule; add a
  test that steps each path for many samples and compares bit-for-bit.

## Step 6: audio-thread complexity and release exports (findings 10, 11)

- AU `cb_output_*_at`: encode once per block into a preallocated packet list,
  index into it.
- Chunker: walk events with one cursor (slice indexes), no `.skip()` on a
  `FilterMap`.
- Gate the hot-reload exports and `__moose_screenshot` behind the `shell` /
  a `screenshot` feature so release format builds don't export them.
  `cargo moose screenshot` must still work (enable the feature there).

## Out of scope for this pass

- Moving VST3 onto the official SDK and the broader API redesign (finding 9,
  dynamic params, CLAP modulation, etc.): specified in
  `2026-11-18-api-redesign.md`, done in a later pass.
- Finding 8 (`PluginCell` asserting) and 13 (minor): leave unless a step
  above touches them.

## Log

### Step 1: serialize state on demand (findings 1, 2)

Changed:
- `PluginLogic::snapshot_into` default returns `false` (no longer delegates to
  `save_state`). Both shells probe the opt-in once at creation (off the audio
  thread): `snapshot_version().is_some() || snapshot_into(..)`. Only opted-in
  plugins publish per block; a versioned `save_state`-only plugin publishes
  through `save_state` when its token moves.
- Shells publish a baseline snapshot at creation; `republish_snapshot` now
  serializes live on the host thread (`SnapshotSlot::store_inline`, blocking
  lock, host only) whatever the opt-in.
- Fresh-snapshot handshake on `SnapshotSlot` (`request_fresh` / `serve` /
  `wait_served`): a save that can't own the plugin asks; the shell serves at
  the end of its next `process` inside `rt::allow_alloc`, once per request.
- Design choice (comment in `moose_core::wrapper`): request + bounded wait
  (`AUDIO_HANDSHAKE_WAIT`, 50 ms) instead of a lock, so the audio thread never
  waits and a running audio thread serves within one block. Fallback is
  `custom_state_view`: the bytes of a load still queued, else the last
  snapshot.
- `StateLoadQueue` tracks applies (`push_tracked` / `mark_applied` /
  `wait_applied` / `unapplied`). Loads while processing queue and wait (50 ms)
  so the editor's `state_changed` fires after the apply; loads while not
  processing apply synchronously on the host thread (`apply_or_queue_state`,
  `try_enter` so an overlapping CLAP `reset` makes it queue instead of panic).
- CLAP: `can_own = !processing` (activated-not-started and stopped both count).
  VST3: new Rust `processing` flag, driven by a new `set_processing` callback
  (shim's `setProcessing` now calls it instead of `reset`; Rust does the reset
  on stop) and set by the first `process` for hosts that skip setProcessing.
  AU: no trustworthy stopped signal, so always the request/queue path.
- Editor `get_state` in CLAP/VST3/AU reads `custom_state_view`.
- Old public API kept source-compatible (`force_push`, `pop`, `apply_state`,
  `save_extra`): `plugins/diffuse` vendors an old moose-clap.

Skipped / limits:
- A CLAP plugin that sleeps (Tail(0)) while processing stays "processing", so a
  save waits 50 ms and then falls back to the last snapshot. For a
  `save_state`-only plugin whose custom state changed inside `process` since
  the last request, that fallback is stale. Marked `ponytail:` in wrapper.rs.
- Editor `set_state` still always queues (it may run on a non-host thread).
- Hot shell reprobes opt-in only on instance creation (dev-only).

### Step 2: report load failures, free off the audio thread (finding 4)

Changed:
- `apply_or_queue_state` returns `Result` and takes the pre-load
  `state::ParamsBackup` (values + `#[persist]`, captured on the host thread
  before the wrapper applies params). When `load_state` rejects the state,
  params and persist are put back, so params, persist and custom state fail
  as one unit, and the error reaches the host: CLAP `state.load` /
  `preset_load.from_location` return `false`, VST3 `setState` kResultFalse,
  AU load / foreign load / factory preset return 0.
- A deferred load that applied within the wait also waits for the fresh
  snapshot, so the editor's `state_changed` → `get_state` reads the new
  custom state, not the pre-load snapshot.
- No torn window for a save: while a load is queued, saves report its
  params (already applied on the host) with its custom bytes
  (`custom_state_view` → `StateLoadQueue::unapplied`), step 1.
- Drop off the audio thread: verified, no change needed. The queue's
  `owners` list holds an `Arc` of every pushed state until a later host
  push or save prunes it, so the audio thread's `pop` clone is never the
  last owner (`audio_cannot_drop_the_last_owner_and_retention_is_bounded`).

Skipped:
- The optional `validate` hook. A deferred load's envelope already parses
  on the host thread, and the load waits for the audio thread's apply, so
  the real `load_state` error reaches the host whenever audio is running.
  Only a load queued while the host isn't running blocks (50 ms timeout)
  still reports success before `load_state` ran; a hook would need a new
  trait method plus hot-reload ABI plumbing for that case. Add it if a
  plugin needs to reject such loads up front.
- The deferred-failure path has no wrapper-level test (needs a live audio
  thread); `wait_applied` itself is unit-tested in moose-core.
